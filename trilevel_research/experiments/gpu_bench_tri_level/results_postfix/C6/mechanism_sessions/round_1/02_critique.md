Here is the rigorous critique of each proposal, based strictly on the trace evidence and practical implementation risks.

### Proposal 1: Replay-Based Interleaved Exploration

1.  **Most likely failure mode**: The replay buffer will confirm the "lucky seed" hypothesis, but the runner currently has no mechanism to *exploit* that knowledge. If the replay shows iter 4 was an outlier (e.g., another seed gives 1.0 bpb), you will have wasted 3 runs only to return to the exact same stuck state. If replay confirms it is robust (e.g., all 3 seeds get ~0.12 bpb), you still have no way to find *better* configs—the runner will remain stuck near that same region because the mutation engine hasn’t changed.

2.  **Implementation trap**: The `_select_next_config` method currently does not distinguish between "new proposal" and "replay" states. Adding a replay queue requires injecting a config that is not generated by `_mutate_config()` → risk of violating the internal state machine (e.g., double-counting iterations, breaking the `config_idx` counter). The hardest part is preventing the replay from masking the real bottleneck: the mutation logic itself.

3.  **Evidence from trace**: Trace shows iter 4 (bpb=0.1286) and immediate neighbors (iter 5, 6, 7) all discarding. This *could* be a seed fluke, but the pattern (17 consecutive discards) suggests the parameter space near 0.003/1e-5 is genuinely bad, not a seed artifact. Replay is unlikely to change this.

4.  **Score**: Impact (2) × Feasibility (4) ÷ Complexity (3) = **2.67**

### Proposal 2: Adaptive Perturbation Budget with Crossover

1.  **Most likely failure mode**: **Crossover between discarded configs will inherit failure modes.** Three discarded configs all died for different reasons (e.g., one had high LR, another had high WD). Crossing them may produce a config that has *both* high LR and high WD → catastrophe (bpb >> 6.0). The adaptive noise increase (2x) could also push the sampler into numerically unstable regimes (e.g., LR > 0.01) that crash the run.

2.  **Implementation trap**: The crossover logic needs to handle mixed-type hyperparameters (float LR, integer HIDDEN_DIM, categorical optimizer). Swapping parameters blindly between configs can produce illegal values (e.g., mixing float and int for the same slot). The `_mutate_config` method returns a single dict; implementing crossover requires maintaining a history buffer of full config dicts and a mating function that knows parameter types. This is easy to get wrong silently.

3.  **Evidence from trace**: Trace shows `discard_streak = 17`. The proposal correctly identifies that perturbations are tiny (LR changes of 0.0001). However, the trace does not show evidence that crossover would have helped: the altimeters (iter 16, bpb=1.1665) are *worse* than the best (0.1286). Crossover between bad parents usually produces bad offspring. There is no indication that discarded configs contain complementary good genes.

4.  **Score**: Impact (4) × Feasibility (2) ÷ Complexity (4) = **2.00**

### Proposal 3: Heterogeneous Parameter-Space Resampling

1.  **Most likely failure mode**: **Forcing uniform resampling after N discards will repeatedly generate configs that have already been tried.** The trace shows the runner has been stuck for 17 iterations. If resampling pulls from the full prior (e.g., LR uniform 1e-4 to 1e-1), it will likely pick a value like LR=0.05 or HIDDEN_DIM=512—values that were *never* sampled in the trace (only LR=0.0025–0.003, HIDDEN_DIM=256). That is actually *good*. The failure mode is that the resampling may conflict with the mutation engine: after resampling, `_mutate_config` will immediately perturb the new config back toward the best, undoing the reset.

2.  **Implementation trap**: The hardest part is ensuring the resampled config bypasses the mutation step but still gets tracked by the `best_config` update logic. If `_is_fresh_exploration_needed` returns True, the runner must generate a config without calling `_mutate_config`. However, the trace shows all proposals go through `_mutate_config`. Adding a conditional branch risks that the resampled config is overwritten or ignored during evaluation.

3.  **Evidence from trace**: Strongest evidence of all proposals. The trace shows the runner *never* explores BATCH_SIZE != 64, HIDDEN_DIM != 256 after iter 3, or LR values outside [0.0025, 0.003]. The baseline bpb=6.4116 suggests the optimal region is far from the current cluster. Resampling would have immediately tested a different regime (e.g., iter 8 could have been LR=0.01, HIDDEN_DIM=128).

4.  **Score**: Impact (5) × Feasibility (5) ÷ Complexity (2) = **12.5**

### Proposal 4: Surrogate-Gated Early Termination

1.  **Most likely failure mode**: **The surrogate will learn the same local optimum bias as the runner.** With 20+ data points all clustered around LR=0.0025–0.003, any surrogate (k-NN, RF, linear) will predict that configurations far from this cluster have high bpb. It will *reject* the very diversity the search needs. The "skip veto" mechanism (1 in 5) is too weak to overcome a biased surrogate. Result: the runner becomes even *more* stuck.

2.  **Implementation trap**: The surrogate must be retrained after every run, and the prediction threshold must be dynamically calibrated (e.g., based on prediction uncertainty). Implementing this correctly requires a time-sensitive model update pipeline—easy to get wrong in `_should_skip_config()` where a stale model rejects a good config. The highest complexity is model persistence across subprocess calls (the GPU runs in a subprocess; the surrogate lives in the main process). If the main process doesn’t update the surrogate before the next proposal, it uses stale data.

3.  **Evidence from trace**: The trace has only 21 data points. That is too few for a reliable surrogate—an RF trained on 21 points with high variance will have near-zero predictive power. The proposal would likely skip all diverse configs, making exploration worse.

4.  **Score**: Impact (3) × Feasibility (2) ÷ Complexity (5) = **1.20**
